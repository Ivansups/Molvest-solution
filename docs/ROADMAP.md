# Техническое задание на разработку AI-агента для техподдержки 1С (Хакатон «Молвест»)

## 1. Назначение документа

Данный документ – единый план реализации AI-агента (чат-бота) для автоматизации технической поддержки пользователей 1С. Он предназначен для команды разработчиков (3 человека) и фиксирует:

- согласованную архитектуру и стек;
- приоритетные сценарии и порядок их реализации;
- функциональные требования к каждому модулю;
- контракты взаимодействия между компонентами;
- критерии оценки (в соответствии с правилами хакатона);
- обязательные тесты и критерии завершения каждого этапа.

Разработка ведётся итеративно, строго по этапам. Переход к следующему этапу допустим только после выполнения критериев готовности текущего.

Этапы 1–8 — план по приоритету. Расхождения с ТЗ заказчика — в **§15**. Открытые пробелы продукта — в **§12**.

## 2. Область реализации

Система представляет собой **веб-приложение** (монолит с чётким разделением на бэкенд, фронтенд и агентный слой), которое предоставляет:

- **чат-интерфейс** для пользователей (публичный виджет `/chat`);
- **административную панель** для управления базой знаний, просмотра логов и метрик;
- **интеллектуальное ядро** на базе GigaChat (RAG, генерация ответов, анализ скриншотов); классификация простых сообщений — правилами, уверенность — по скору поиска;
- **механизм эскалации** операторам при низкой уверенности.

### 2.1. Что входит в реализацию

- Обработка текстовых запросов пользователей с поиском по базе знаний (RAG).
- Анализ загруженных изображений (скриншотов 1С) с использованием GigaChat Vision.
- Генерация ответов с указанием источника (документ БЗ).
- Оценка уверенности GigaChat в ответе; при пороге < 80% – эскалация (имитация передачи оператору).
- Интерфейс администратора для загрузки/удаления/реиндексации документов БЗ (Word, PDF, HTML, Markdown). Правка метаданных через PATCH не сделана.
- Просмотр истории диалогов. Агрегат метрик считает `GET /api/metrics`; дашборд `/` и `/analytics` показывают три метрики из этого API. Grafana — перспектива, не сделана.
- Демо-канал — публичный веб-виджет. Вебхук Bitrix и почта Redmine не сделаны.
- Черновик оператора в нашей консоли (`draft` / `auto` / `agent`, см. `OPERATOR_ASSIST_MODE`) — имитация сценария 2 ТЗ, не подписка на чужой чат Bitrix.
- **Авторизация сотрудников** — на стороне Next.js через **Auth.js** (NextAuth v5), пользователи в **Prisma** (см. п. 3.1, 3.4).
- **Настройки панели** — порог и режим эскалации через `GET`/`PUT /api/settings` (runtime поверх env).

### 2.2. Что не реализуется

- Полноценная интеграция с Bitrix24/Redmine (нет вебхука и почты; демо — виджет).
- Хранение больших объёмов данных (тестовое наполнение БЗ — на команде).

## 3. Согласованная архитектура

### 3.1. Технологический стек

- **Backend**: Python 3.12+, FastAPI, SQLAlchemy (async), Alembic.
- **База данных**: PostgreSQL 16 с расширением pgvector (образ `pgvector/pgvector:pg16`).
- **Агентный слой**: LangGraph – оркестрация сценариев (вопрос-ответ, анализ изображений, эскалация, черновик оператора).
- **AI-модель**: GigaChat (API) – эмбеддинги, генерация ответа, Vision. На текстовый вопрос по 1С — **один** вызов модели (generate). Classify и оценку уверенности отдельными запросами к GigaChat не делаем.
- **Frontend**: React (Next.js, App Router) + Tailwind, каталог `frontend/`.
- **Авторизация**: Auth.js v5 на стороне Next.js + **Prisma**. Prisma работает только с auth-таблицами (`User`, `Account`, `Session`, `VerificationToken`) в схеме PostgreSQL `auth` (`AUTH_DATABASE_URL`). Домен-модели (Document, Chunk, Conversation, Message, Escalation) ведёт SQLAlchemy/Alembic в `public`.
- **Инфраструктура**: Docker Compose (`db`, `redis`, `api`, `web`), GitHub, README. Python — **uv**, Node — **pnpm**. Redis — кэш эмбеддингов запросов и готовых ответов, не хранилище чанков.
- **GigaChat SDK**: пакет `gigachat` (ставится через `uv`, не pip). Один SDK на чат, Vision и эмбеддинги.
- **API-стиль Next.js ↔ FastAPI**: обычный **REST** (JSON). Next.js проксирует `/backend/*` и admin-маршруты на FastAPI. Типизация — OpenAPI FastAPI (`/docs`, `/openapi.json`). tRPC не используем.

### 3.2. Взаимодействие компонентов

- **Пользователь** ↔ **React-виджет** ↔ **FastAPI (синхронно, REST)**.
- **FastAPI** ↔ **LangGraph** (внутренний вызов).
- **LangGraph** ↔ **GigaChat API** (через единый клиент).
- **FastAPI** ↔ **PostgreSQL+pgvector** (CRUD документов, хранение чанков, эмбеддингов, диалогов, эскалаций).
- **FastAPI** ↔ **Redis** (кэш; источник истины для документов и чанков — только Postgres).
- **Администратор** ↔ **React-консоль** (сессия Auth.js, layout `frontend/app/(console)/`) ↔ **FastAPI (REST)** через внутренний токен.
- **Next.js-сервер** ↔ **Prisma** ↔ **PostgreSQL**, схема `auth`.
- **Next.js-сервер** → **FastAPI**: заголовок `X-Internal-Token` после проверки сессии на стороне Next.js. FastAPI сессии Auth.js не разбирает. Пустой `INTERNAL_SERVICE_TOKEN` — проверка на API отключена (локальная разработка).

### 3.3. Ключевые модули (приложения)

- **core** – конфигурация, логирование, клиент GigaChat, клиент Redis, общие утилиты.
  - `GigaChatService` — единая сервис-обёртка над SDK `gigachat`, один экземпляр на процесс. Все остальные модули вызывают только её, не SDK и не сырой `httpx` напрямую:
    - `get_embeddings(texts: list[str]) -> list[list[float]]`
    - `chat_with_vision(image_base64: str, prompt: str) -> str`
    - `generate(messages: Sequence[ChatTurn]) -> str`
- **knowledge_base** – модели Document, Chunk; CRUD документов; индексация (чанкинг + эмбеддинги + сохранение в pgvector); счётчик `kb_version` при успешной индексации/удалении.
- **rag** – ретривал (поиск релевантных чанков + скор), генерация ответа. Уверенность берётся из скора поиска, не из второго вызова модели.
- **agent** – LangGraph-граф, объединяющий сценарии (текст, изображения, эскалация).
- **vision** – обработка скриншотов (извлечение текста и визуальной информации через GigaChat Vision).
- **conversations** – модели диалогов, сообщений, эскалаций; сервисы логирования, метрик и ответа оператора (`suggested_response`, роли `operator`).
- **channels** – в коде нет отдельного пакета. Канал демо — виджет в `frontend/`. Адаптеры Bitrix/Redmine не реализованы.
- **admin** – FastAPI `/api/documents`, `/api/conversations`, `/api/metrics`; UI — консоль Next.js (`/`, `/knowledge-base`, `/chat/support`, `/operator`).
- **auth (`frontend/`)** – Auth.js + Prisma; страница `/login`; защита консоли редиректом в `app/(console)/layout.tsx` (не `middleware.ts` и не префикс `/admin/**`).

### 3.4. Авторизация (Auth.js + Prisma)

- `frontend/prisma/schema.prisma` — только auth: `User`, `Account`, `Session`, `VerificationToken` (таблицы `auth_users` и т.д. в схеме `auth`).
- `frontend/auth.ts` — Auth.js, провайдер credentials, Prisma Adapter. Сессия — **JWT** (credentials не пишет строку в `auth_sessions`).
- Неавторизованный заход в `(console)` → редирект на `/login`.
- Миграции auth — `prisma migrate`, независимо от Alembic; конфликт имён снят схемой `auth`.
- FastAPI не хранит пользователей и не проверяет куку Auth.js — только `X-Internal-Token`.

## 4. Порядок реализации этапов

Разработка ведётся параллельно тремя разработчиками, но строго по приоритетам:

1. **Инфраструктура и контракты** – настройка базы, конфигов, Docker, Alembic.
2. **Ядро RAG и чат-бота** – обязательный сценарий, основа оценки.
3. **Управление БЗ (админка)** – легко демонстрируется, даёт баллы за UI/UX.
4. **Анализ изображений** – повышает качество использования GigaChat.
5. **Интерфейсы (чат-виджет и админка)** – фронтенд.
6. **Интеграции (упрощённо)** – имитация Bitrix/Redmine.
7. **Бонусные функции** – развитие решения.

## Этап 1. Инфраструктура и общие контракты

### 1.1. Цель этапа

Создать работающую среду разработки, настроить базу данных, определить единый формат запросов/ответов между фронтендом и бэкендом.

### 1.2. Реализуемые задачи

- Настройка **Docker Compose**: Postgres (pgvector), Redis, FastAPI, Next.js (`web`).
- Файл **`.env`** в корне (шаблон `.env.example`): `GIGACHAT_API_KEY`, `GIGACHAT_API_URL`, `DATABASE_URL`, `REDIS_URL`, `CONFIDENCE_THRESHOLD` (0.8), `TOP_K` (5), `MAX_CHUNK_SIZE` (180), `CHUNK_OVERLAP` (40), `OPERATOR_ASSIST_MODE` (`draft`|`auto`|`agent`), `AUTH_SECRET`, `AUTH_DATABASE_URL`, `INTERNAL_SERVICE_TOKEN` (Next.js → FastAPI).
- Инициализация **Alembic** и миграции доменных моделей.
- **Prisma** в `frontend/` (`prisma migrate` в схему `auth`).
- Определение **единого контракта** для `POST /chat`:

```json
{
  "message_id": "uuid",
  "workspace_id": "string",         // для изоляции
  "conversation_id": "uuid | null", // если новый диалог – null
  "text": "string | null",
  "image_base64": "string | null",  // чистый base64, БЕЗ префикса data:image/png;base64,
  "user_id": "string"
}
```

> `image_base64` — сырая base64-строка без префикса `data:image/...;base64,`. Клиент перед отправкой сжимает скриншот (canvas, длинная сторона ≤ 1024, JPEG). `GigaChatService.chat_with_vision` собирает data-URL сам: MIME по сигнатуре (`image/jpeg` если payload начинается с `/9j/`, иначе `image/png`). В `Message.image_url` картинку не пишем — поле под ссылку, не под base64.

Ответ:

```json
{
  "conversation_id": "uuid",
  "message_id": "uuid",
  "text": "string",
  "confidence": 0.87,
  "escalated": false,
  "sources": [{"document_id": "uuid", "title": "string", "chunk_text": "..."}]
}
```

При эскалации гостю уходит текст «Вопрос передан оператору техподдержки.» (`GUEST_ESCALATION_TEXT`), не «Передано оператору».

- Обработчик ошибок и логирование: `request_id` в логе и заголовке `x-request-id`. Отдельного `correlation_id` нет.
- **README.md** с запуском (`make setup` / `docker compose up`).

### 1.3. Критерии завершения

- `docker compose up` поднимает Postgres, Redis, API и Next.js.
- `GET /health` возвращает `200 OK` (`{"status":"ok"}`).
- Alembic успешно применяет миграции (entrypoint контейнера API).
- Prisma применяет auth-миграции, вход credentials на `/login` работает локально.
- Контракт `POST /chat` задокументирован в README и OpenAPI.

## Этап 3. RAG-пайплайн и использование GigaChat (Agent Core)

### 3.1. Цель

Реализовать интеллектуальное ядро: индексация документов, ретривал, генерация ответа с оценкой уверенности, эскалация.

### 3.2. Индексация (Ingestion)

- При загрузке документа или по команде `reindex`:
  - Разбить содержимое на чанки: по умолчанию **180 слов**, перекрытие **40** (`MAX_CHUNK_SIZE`, `CHUNK_OVERLAP`). Окно модели Embeddings — 512 токенов; 512 слов в чанк не влезает.
  - Для каждого чанка получить эмбеддинг через `GigaChatService.get_embeddings()`.
  - В одной транзакции удалить старые чанки документа и вставить новые (retrieval не видит половину документа). Не `INSERT ... ON CONFLICT`.
  - После успешной индексации или удаления увеличить `kb_version` в Redis. Им сбрасывается кэш ответов; кэш эмбеддингов **запроса** не трогаем.
- Процесс — FastAPI `BackgroundTasks`: ответ админу «документ принят» не ждёт эмбеддинги.

**Про эмбеддинги GigaChat**: отдельный эндпоинт `POST /embeddings` в API GigaChat, тарифицируется отдельно от генерации текста — не забывать при оценке лимитов токенов (см. риски, п. 11). Доступно несколько моделей эмбеддингов; для проекта фиксируем одну модель на весь срок хакатона — смена модели эмбеддингов требует полной реиндексации базы знаний (размерность/пространство векторов меняется).

### 3.3. Ретривал

- Получить эмбеддинг запроса: сначала Redis `emb:{hash(нормализованный текст)}`, при промахе — `GigaChatService.get_embeddings()`, записать в Redis (TTL ~1 час). Этот кэш **не** сбрасывать при реиндексе.
- Поиск по pgvector: косинусное расстояние (`cosine_distance`), `LIMIT top_k`. Индекс IVFFlat/HNSW не делаем.
- Вернуть top_k чанков (по умолчанию 5, `TOP_K`) с текстом, названием документа и скором `1 - distance`.
- Векторы документов только в pgvector.
- Кэш `ret:{kb_version}:{hash(запрос)}` не реализован.

### 3.4. Генерация и оценка уверенности (LangGraph)

На один текстовый вопрос по 1С — **один** вызов GigaChat (`generate`). Отдельные запросы модели на classify и на «насколько ты уверен» не делаем: это лишние 1–4 секунды на каждый ход.

- **Граф агента** (LangGraph):
  1. `vision` — только если в запросе есть картинка; иначе шаг пропускается.
  2. `classify` — **без LLM**: ключевые фразы / правила (приветствие, благодарность, пустое сообщение, явный оффтоп). Совпало → готовый шаблон, граф заканчивается. Иначе `intent = support`.
  3. Кэш ответа Redis `ans:{kb_version}:{installation_id}:{hash(нормализованный вопрос)}`. Попадание → ответ с источниками. Приветствия, эскалации и ходы с историей диалога не кэшируем.
  4. `retrieve` — эмбеддинг запроса (Redis или GigaChat) + top_k чанков.
  5. Если скор лучшего чанка ниже `CONFIDENCE_THRESHOLD` — эскалация **без** `generate`.
  6. `generate` — один вызов GigaChat: вопрос + чанки. Уточнения — последние 3–4 сообщения из БД.
  7. `confidence` = скор лучшего чанка. Если generate не вызывали — `escalated=true`, запись Escalation, гостю «Вопрос передан оператору техподдержки.»
- В режиме `OPERATOR_ASSIST_MODE=draft` повтор гостя в уже `escalated` диалоге граф не гоняет: пишется только реплика пользователя.
- Все вызовы GigaChat — через `core/gigachat_client`. Отдельный пул `httpx` не заводим.
- **Не делаем:** индекс IVFFlat, узел `confidence_check` с вызовом модели, `POST /chat/stream`.

### 3.5. Обработка изображений (скриншотов)

GigaChat Vision — мультимодальная модель: принимает текст + изображение, отдаёт текст. Отдельный OCR не нужен, модель сама читает текст/ошибки/интерфейс на скриншоте. Не требует S3 или файлового хранилища — картинка целиком прогоняется через API как текстовая (base64) строка внутри JSON, ничего заранее сохранять не нужно.

**Путь картинки по системе:**

1. **Next.js (клиент)** — файл сжимается (`fileToCompressedDataUrl`, длинная сторона ≤ 1024, JPEG), в `image_base64` уходит чистый base64 без data-URL префикса.
2. **FastAPI** — строка как есть, в граф → узел `vision`.
3. **`GigaChatService.chat_with_vision`** — собирает `data:{mime};base64,{payload}` (JPEG по сигнатуре `/9j/`, иначе PNG) и шлёт multimodal-сообщение в SDK.
4. Текст описания идёт в тот же RAG-путь (`retrieve` → порог → `generate` или эскалация). Отдельной ветки пайплайна нет (`docs/SCENARIOS.md`, сценарий 3).

**Промпт**: *«Опиши, что изображено на скриншоте, выдели ошибки, поля, коды. Если видишь ошибку 1С, объясни вероятную причину и предложи решение.»*

**Ограничения**:
- Тяжёлые скриншоты сжимаем на клиенте.
- Форматы на входе — PNG и JPEG (клиент отдаёт JPEG после сжатия).
- Vision занимает секунды — таймаут `/chat` на клиенте 60 с; отдельного индикатора «печатает» в виджете нет (кнопка «Отправить» блокируется на время запроса).
- Скриншот в БД не сохраняем.

### 3.6. Тесты

- Индексация документа: проверка создания чанков и эмбеддингов; повторная индексация увеличивает `kb_version`.
- Ретривал: поиск по чанкам возвращает релевантные; эмбеддинг запроса берётся из кэша при повторном тексте.
- Classify: приветствие и пустой ввод не вызывают GigaChat.
- Генерация: ответ содержит ссылки на источники; на вопрос `support` — один вызов generate.
- Уверенность: слабый скор ретривала даёт эскалацию без generate.
- Анализ изображения: корректный вызов Vision и интеграция в граф.

### 3.7. Критерий завершения

- Через API можно загрузить документ, дождаться индексации (или запустить вручную).
- После индексации текстовый запрос возвращает осмысленный ответ с указанием источника; `confidence` — скор ретривала.
- При скоре < 0.8 — эскалация без вызова generate.
- Приветствие / пустой ввод не ходят в GigaChat.
- Изображение обрабатывается и даёт ответ.

## 11. Риски и их смягчение

- **GigaChat API лимиты и время ответа**: classify — правила, не модель. Уверенность — скор ретривала, не второй вызов. Эмбеддинги запросов и повторяющиеся ответы — Redis (`kb_version` сбрасывает ответы при изменении БЗ). На вопрос по 1С без картинки — один generate. В виджете — индикатор загрузки; SSE — опционально отдельным маршрутом, не внутри `POST /chat`.
- **Бюджет задержки (текст, без картинки)**: приветствие / «спасибо» — меньше 100 мс; повтор вопроса при той же БЗ — меньше 200 мс из Redis; слабый поиск — эскалация без generate; новый вопрос — retrieve + один generate; скриншот — узкое место Vision, сжатие на клиенте (п. 3.5).
- **Сложность интеграции Bitrix/Redmine**: делать упрощённо, оставляя ядро на виджете.
- **Отсутствие данных для БЗ**: наполнить тестовыми данными из предоставленных источников (инструкции, документация 1С).
- **Две ORM на одной БД (Prisma + SQLAlchemy)**: Prisma — схема `auth`, Alembic — `public`. Не давать Prisma-схеме трогать домен-таблицы.

## 14. Идентичность диалога (виджет и внешние каналы)

Одно окно переписки = один `conversation_id` у нас в БД. Агент (`POST /chat`) работает только с этим id. Канал (виджет, Bitrix24, Redmine) сам решает, как его запомнить. Наш UUID во внешнюю систему как её номер чата не подставляем — у каждой платформы своя нумерация.

### 14.1. Как это работает сейчас в виджете

1. Первое сообщение гостя уходит с `conversation_id: null`.
2. Бэкенд создаёт запись `Conversation`, в ответе отдаёт UUID.
3. Виджет сохраняет его (`guestConversationId` в состоянии страницы) и в следующих сообщениях шлёт уже этот id — так подтягивается история (последние 3–4 реплики в `generate`).
4. У оператора тот же UUID в адресе: `/chat/support/{conversation_id}`.

Пока гость держит id только в памяти вкладки: обновление страницы начинает новый диалог. Для демо виджета этого достаточно.

### 14.2. Как повторить на Bitrix24 / Redmine

У канала уже есть свой устойчивый id треда. Адаптер (этап 7) не меняет `POST /chat`, а только переводит «их id» в «наш UUID»:

| Канал | Их id треда | Что кладём в `conversation_id` |
| --- | --- | --- |
| Веб-виджет | то, что хранит браузер | наш UUID, как в п. 14.1 |
| Bitrix24 | id чата / сессии открытой линии | наш UUID после первого сообщения |
| Redmine HelpDesk | номер тикета (письмо → тикет) | тот же наш UUID |

Таблица соответствия — `ChannelThread` (`bitrix_ol_bot` / `bitrix_openlines` /
`redmine` / `bitrix`).

Поток:

1. Пришло сообщение из канала с их id треда.
2. Адаптер ищет связку. Нет записи — вызываем `POST /chat` с `conversation_id: null`, сохраняем пару «их id → UUID из ответа».
3. Есть запись — в `POST /chat` подставляем уже наш UUID. История не рвётся.
4. Ответ агента уходит обратно в **тот же** чат/тикет канала. Пользователь наш UUID не видит.

Без таблицы каждое входящее сообщение станет новым диалогом, и оператор увидит обрывки. С таблицей внешняя платформа даже надёжнее виджета: их id не пропадает при обновлении страницы.
