# Техническое задание на разработку AI-агента для техподдержки 1С (Хакатон «Молвест»)

## 1. Назначение документа

Данный документ – единый план реализации AI-агента (чат-бота) для автоматизации технической поддержки пользователей 1С. Он предназначен для команды разработчиков (3 человека) и фиксирует:

- согласованную архитектуру и стек;
- приоритетные сценарии и порядок их реализации;
- функциональные требования к каждому модулю;
- контракты взаимодействия между компонентами;
- критерии оценки (в соответствии с правилами хакатона);
- обязательные тесты и критерии завершения каждого этапа.

Разработка ведётся итеративно, строго по этапам. Переход к следующему этапу допустим только после выполнения критериев готовности текущего.

## 2. Область реализации

Система представляет собой **веб-приложение** (монолит с чётким разделением на бэкенд, фронтенд и агентный слой), которое предоставляет:

- **чат-интерфейс** для пользователей (в виде веб-виджета, имитирующего интеграцию с Bitrix24/Redmine);
- **административную панель** для управления базой знаний, просмотра логов и метрик;
- **интеллектуальное ядро** на базе GigaChat (RAG, генерация ответов, анализ скриншотов); классификация простых сообщений — правилами, уверенность — по скору поиска;
- **механизм эскалации** операторам при низкой уверенности.

### 2.1. Что входит в реализацию

- Обработка текстовых запросов пользователей с поиском по базе знаний (RAG).
- Анализ загруженных изображений (скриншотов 1С) с использованием GigaChat Vision.
- Генерация ответов с указанием источника (документ БЗ).
- Оценка уверенности GigaChat в ответе; при пороге < 80% – эскалация (имитация передачи оператору).
- Интерфейс администратора для загрузки/редактирования/удаления документов БЗ (Word, PDF, HTML, Markdown).
- Просмотр истории диалогов и метрик (процент автоответов, среднее время ответа, количество эскалаций).
- Упрощённая имитация интеграции с Bitrix24 и Redmine (для демонстрации – вебхуки или заглушки).
- **Авторизация администратора** — на стороне Next.js через **NextAuth**, хранение пользователей/сессий через **Prisma** (см. п. 3.1, 3.4).

### 2.2. Что не реализуется

- Полноценная интеграция с реальными системами Bitrix24/Redmine (делается упрощённо, через моки).
- Хранение больших объёмов данных (тестовое наполнение БЗ предоставляется командой).

## 3. Согласованная архитектура

### 3.1. Технологический стек

- **Backend**: Python 3.12+, FastAPI, SQLAlchemy (async), Alembic.
- **База данных**: PostgreSQL 15+ с расширением pgvector.
- **Агентный слой**: LangGraph – оркестрация сценариев (вопрос-ответ, анализ изображений, эскалация).
- **AI-модель**: GigaChat (API) – эмбеддинги, генерация ответа, Vision. На текстовый вопрос по 1С — **один** вызов модели (generate). Classify и оценку уверенности отдельными запросами к GigaChat не делаем.
- **Frontend**: React (Next.js) с Tailwind CSS.
- **Авторизация**: NextAuth.js (на стороне Next.js) + **Prisma** — Prisma работает только с auth-таблицами NextAuth (`User`, `Account`, `Session`, `VerificationToken`) в той же PostgreSQL, не трогает домен-модели (Document, Chunk, Conversation, Message, Escalation), которыми управляет SQLAlchemy/Alembic.
- **Инфраструктура**: Docker Compose (FastAPI, PostgreSQL, Redis), GitHub, README с инструкцией развертывания. Redis — кэш эмбеддингов запросов и готовых ответов, не хранилище чанков.
- **GigaChat SDK**: `pip install gigachat` — официальная Python-библиотека, используется и для обычного чата, и для Vision, и для эмбеддингов (один SDK на все режимы).
- **API-стиль Next.js ↔ FastAPI**: обычный **REST** (JSON через `fetch`/`axios`), не tRPC. На дедлайне хакатона это надёжнее и быстрее в реализации; типизация закрывается через OpenAPI-схему FastAPI (`drf-spectacular`-аналог из коробки — `/docs`, `/openapi.json`). tRPC даёт полную типобезопасность, но требует лишней настройки на старте — не оправдано для 7 дней.

### 3.2. Взаимодействие компонентов

- **Пользователь** ↔ **React-виджет** ↔ **FastAPI (синхронно, REST)**.
- **FastAPI** ↔ **LangGraph** (внутренний вызов).
- **LangGraph** ↔ **GigaChat API** (через единый клиент).
- **FastAPI** ↔ **PostgreSQL+pgvector** (CRUD документов, хранение чанков, эмбеддингов, диалогов, эскалаций).
- **FastAPI** ↔ **Redis** (кэш; источник истины для документов и чанков — только Postgres).
- **Администратор** ↔ **React-админка** (защищена **NextAuth**-сессией) ↔ **FastAPI (REST)**.
- **Next.js-сервер** ↔ **Prisma** ↔ **PostgreSQL** (только auth-таблицы NextAuth).
- **Next.js-сервер** → **FastAPI**: доверенный service-to-service вызов (внутренний токен) после проверки NextAuth-сессии на стороне Next.js — сам FastAPI сессии NextAuth не разбирает.

### 3.3. Ключевые модули (приложения)

- **core** – конфигурация, логирование, клиент GigaChat, клиент Redis, общие утилиты.
  - `GigaChatService` — единая сервис-обёртка над SDK `gigachat`, один экземпляр на процесс. Все остальные модули вызывают только её, не SDK и не сырой `httpx` напрямую:
    - `get_embeddings(texts: list[str]) -> list[list[float]]`
    - `chat_with_vision(image_base64: str, prompt: str) -> str`
    - `generate(messages: list[Message]) -> str`
- **knowledge_base** – модели Document, Chunk; CRUD документов; индексация (чанкинг + эмбеддинги + сохранение в pgvector); счётчик `kb_version` при успешной индексации/удалении.
- **rag** – ретривал (поиск релевантных чанков + скор), генерация ответа. Уверенность берётся из скора поиска, не из второго вызова модели.
- **agent** – LangGraph-граф, объединяющий сценарии (текст, изображения, эскалация).
- **vision** – обработка скриншотов (извлечение текста и визуальной информации через GigaChat Vision).
- **conversations** – модели диалогов, сообщений, эскалаций; сервисы логирования и метрик.
- **channels** – адаптеры для имитации Bitrix24 и Redmine (веб-виджет, email-заглушка).
- **admin** – API и UI для управления БЗ и просмотра статистики.
- **auth (apps/web)** – NextAuth + Prisma; login-страница, middleware, защита admin-роутов. Живёт целиком на стороне Next.js, отдельно от Python-модулей.

### 3.4. Авторизация (NextAuth + Prisma)

- `apps/web/prisma/schema.prisma` — схема только для auth: `User`, `Account`, `Session`, `VerificationToken` (стандартная схема NextAuth Prisma Adapter).
- `apps/web/lib/auth.ts` — конфигурация NextAuth (провайдер credentials/email — на выбор фронтенд-разработчика), Prisma Adapter.
- `apps/web/middleware.ts` — защита `/admin/**` неавторизованным доступом.
- Миграции auth-схемы — через `prisma migrate`, независимо от `alembic` (разные наборы таблиц в одной БД, конфликтов имён нет).
- FastAPI не хранит пользователей и не валидирует пароли/токены NextAuth — только принимает внутренний service-токен от Next.js-сервера.

## 4. Порядок реализации этапов

Разработка ведётся параллельно тремя разработчиками, но строго по приоритетам:

1. **Инфраструктура и контракты** – настройка базы, конфигов, Docker, Alembic.
2. **Ядро RAG и чат-бота** – обязательный сценарий, основа оценки.
3. **Управление БЗ (админка)** – легко демонстрируется, даёт баллы за UI/UX.
4. **Анализ изображений** – повышает качество использования GigaChat.
5. **Интерфейсы (чат-виджет и админка)** – фронтенд.
6. **Интеграции (упрощённо)** – имитация Bitrix/Redmine.
7. **Бонусные функции** – развитие решения.

## Этап 3. RAG-пайплайн и использование GigaChat (Agent Core)

### 3.1. Цель

Реализовать интеллектуальное ядро: индексация документов, ретривал, генерация ответа с оценкой уверенности, эскалация.

### 3.2. Индексация (Ingestion)

- При загрузке документа или по команде `reindex`:
  - Разбить содержимое на чанки (размер – настраивается, 512 токенов, перекрытие 128).
  - Для каждого чанка получить эмбеддинг через `GigaChatService.get_embeddings()`.
  - Сохранить чанк и эмбеддинг в pgvector (использовать `INSERT ... ON CONFLICT`).
  - После успешной индексации или удаления документа увеличить `kb_version` (ключ в Redis). Им инвалидируются кэш ответов и опциональный кэш ретривала; кэш эмбеддингов **запроса** не трогаем.
- Весь процесс выполняется асинхронно через FastAPI `BackgroundTasks` (Celery на хакатоне не нужен): ответ админу «документ принят» не ждёт эмбеддинги.

**Про эмбеддинги GigaChat**: отдельный эндпоинт `POST /embeddings` в API GigaChat, тарифицируется отдельно от генерации текста — не забывать при оценке лимитов токенов (см. риски, п. 11). Доступно несколько моделей эмбеддингов; для проекта фиксируем одну модель на весь срок хакатона — смена модели эмбеддингов требует полной реиндексации базы знаний (размерность/пространство векторов меняется).

### 3.3. Ретривал

- Получить эмбеддинг запроса: сначала Redis `emb:{hash(нормализованный текст)}`, при промахе — `GigaChatService.get_embeddings()`, записать в Redis (TTL ~1 час). Этот кэш **не** сбрасывать при реиндексе: вектор той же фразы не зависит от содержимого БЗ.
- Выполнить поиск по pgvector (`ORDER BY embedding <-> query_embedding LIMIT top_k`). Индекс IVFFlat/HNSW на объёме хакатона не делаем.
- Вернуть top_k чанков (по умолчанию 5, константа `TOP_K`) с текстом, метаданными и скором сходства.
- Векторы **документов** хранятся только в pgvector — в Redis их не дублируем.
- Если останется время: кэш списка `(chunk_id, score)` с ключом `ret:{kb_version}:{hash(запрос)}`. Сбрасывается вместе с `kb_version`.

### 3.4. Генерация и оценка уверенности (LangGraph)

На один текстовый вопрос по 1С — **один** вызов GigaChat (`generate`). Отдельные запросы модели на classify и на «насколько ты уверен» не делаем: это лишние 1–4 секунды на каждый ход.

- **Граф агента** (LangGraph):
  1. `vision` — только если в запросе есть картинка; иначе шаг пропускается.
  2. `classify` — **без LLM**: ключевые фразы / правила (приветствие, благодарность, пустое сообщение, явный оффтоп). Совпало → готовый шаблон, граф заканчивается. Иначе `intent = support`.
  3. Кэш ответа Redis `ans:{kb_version}:{hash(нормализованный вопрос)}`. Попадание → сразу ответ с источниками. Приветствия и эскалированные ответы не кэшируем.
  4. `retrieve` — эмбеддинг запроса (Redis или GigaChat) + top_k чанков.
  5. Если скор лучшего чанка ниже `CONFIDENCE_THRESHOLD` — эскалация **без** `generate`.
  6. `generate` — один вызов GigaChat: вопрос + чанки. Если в диалоге нужны уточнения — последние 3–4 сообщения из БД, без саммари отдельным вызовом модели.
  7. В ответ кладём `confidence` = скор лучшего чанка (не второй промпт). Если generate не вызывали — `escalated=true`, запись Escalation, текст «Передано оператору».
- Все вызовы GigaChat проходят через единый клиент (`core/gigachat_client`). Отдельный пул `httpx` рядом с SDK не заводим.
- **Не в этом этапе:** индекс IVFFlat, отдельный узел `confidence_check` с вызовом модели. Контракт `POST /chat` остаётся одним JSON (каналы, логи, эскалация).

**Стриминг SSE (по возможности, не критерий этапа).** После порога ретривала решение «отвечаем сами / эскалируем» уже известно, поэтому токены можно отдавать без риска показать ответ и потом забрать его. Имеет смысл отдельный маршрут, например `POST /chat/stream` (`text/event-stream`): сначала кадр с `confidence`, `escalated`, `sources`; при `escalated=true` стрима текста нет; иначе — дельты токенов и финальный кадр. Обычный `POST /chat` не ломаем: им пользуются Bitrix/почта и любой клиент, которому нужен готовый JSON. Виджет может перейти на стрим, когда базовый чат уже работает. Обрыв и ошибка посередине — отдельная обработка (дописать сообщение / показать сбой), кэш попадания отдаём одним кадром, без стрима.

### 3.5. Обработка изображений (скриншотов)

GigaChat Vision — мультимодальная модель: принимает текст + изображение, отдаёт текст. Отдельный OCR не нужен, модель сама читает текст/ошибки/интерфейс на скриншоте. Не требует S3 или файлового хранилища — картинка целиком прогоняется через API как текстовая (base64) строка внутри JSON, ничего заранее сохранять не нужно.

**Путь картинки по системе:**

1. **Next.js (клиент)** — файл из `<input type="file">` читается через `FileReader.readAsDataURL()`, результат `data:image/png;base64,iVBORw0KGgo...` — берём часть после запятой (чистый base64, без префикса) и кладём в поле `image_base64` контракта `POST /chat` (см. Этап 1.2).
2. **FastAPI** — принимает `image_base64` как обычную строку в Pydantic-модели запроса, ничего с ней не делает, кроме передачи дальше в `GigaChatService.chat_with_vision(...)`.
3. **`GigaChatService.chat_with_vision`** — перед вызовом SDK **добавляет обратно префикс** `data:image/png;base64,` (GigaChat ожидает полноценный data-URL, а не голую base64-строку) и формирует сообщение в формате контента с несколькими частями:
   ```python
   response = gc.chat({
       "messages": [{
           "role": "user",
           "content": [
               {"type": "text", "text": prompt},
               {"type": "image_url", "image_url": {
                   "url": f"data:image/png;base64,{image_base64}"
               }},
           ],
       }]
   })
   ```
4. **GigaChat → FastAPI** — модель возвращает обычный текстовый ответ (описание проблемы/рекомендация).
5. Полученный текст передаётся как часть запроса в тот же граф LangGraph (через узел `retrieve` – ищет по описанию проблемы). Изображение не образует отдельную ветку пайплайна — оно просто становится текстовым входом для общего RAG-пути (см. `docs/SCENARIOS.md`, сценарий 3).

**Промпт**: *«Опиши, что изображено на скриншоте, выдели ошибки, поля, коды. Если видишь ошибку 1С, объясни вероятную причину и предложи решение.»*

**Ограничения**:
- Размер изображения — не больше ~10–20 МБ; тяжёлые скриншоты сжимать на клиенте перед кодированием (canvas / `browser-image-compression`).
- Поддерживаемые форматы — PNG, JPEG, WEBP (проверить актуальный список в документации GigaChat).
- Обработка Vision может занимать несколько секунд — таймауты и на клиенте, и на бэкенде должны это учитывать (индикатор загрузки в виджете).
- Декодировать base64 обратно в файл на бэкенде нужно, только если решено постоянно хранить скриншот (например, для истории диалога) — для самого вызова Vision это не требуется.

### 3.6. Тесты

- Индексация документа: проверка создания чанков и эмбеддингов; повторная индексация увеличивает `kb_version`.
- Ретривал: поиск по чанкам возвращает релевантные; эмбеддинг запроса берётся из кэша при повторном тексте.
- Classify: приветствие и пустой ввод не вызывают GigaChat.
- Генерация: ответ содержит ссылки на источники; на вопрос `support` — один вызов generate.
- Уверенность: слабый скор ретривала даёт эскалацию без generate.
- Анализ изображения: корректный вызов Vision и интеграция в граф.

### 3.7. Критерий завершения

- Через API можно загрузить документ, дождаться индексации (или запустить вручную).
- После индексации текстовый запрос возвращает осмысленный ответ с указанием источника; `confidence` — скор ретривала.
- При скоре < 0.8 — эскалация без вызова generate.
- Приветствие / пустой ввод не ходят в GigaChat.
- Изображение обрабатывается и даёт ответ.

## Этап 5. Чат-виджет и пользовательский интерфейс

### 5.1. Цель

Создать веб-виджет для конечного пользователя, в котором можно задавать вопросы, загружать скриншоты и получать ответы с индикацией эскалации.

### 5.2. Функционал

- Поле ввода текста и кнопка "Отправить".
- Кнопка "Прикрепить изображение" (загрузка файла, предпросмотр).
- Отображение истории сообщений (пользователь – ассистент).
- Индикация эскалации: при уверенности < порога – сообщение "Вопрос передан оператору техподдержки".
- Индикатор загрузки («печатает»), пока виджет ждёт полный JSON `POST /chat`. Стриминг SSE — по возможности (см. этап 3.4): отдельный `POST /chat/stream`, только на пути «отвечаем сами», не вместо основного контракта.
- Отображение источников ответа (название документа, цитата) – можно сделать в виде ссылок или всплывающих подсказок.
- Адаптивный дизайн.

Виджет чата — публичный, без авторизации (конечные пользователи техподдержки не логинятся); NextAuth защищает только `/admin/**`.

### 5.3. Взаимодействие с бэкендом

- Использовать контракт `POST /chat` (этап 1), обычный REST/JSON (см. п. 3.1 — без tRPC).
- При загрузке изображения – кодировать файл в base64 на клиенте и передавать чистую строку (без `data:image/...;base64,` префикса) в поле `image_base64`:
  ```ts
  const toBase64 = (file: File): Promise<string> =>
    new Promise((resolve, reject) => {
      const reader = new FileReader();
      reader.readAsDataURL(file);
      reader.onload = () => resolve((reader.result as string).split(',')[1]);
      reader.onerror = reject;
    });
  ```
  Дальше — обычный `fetch('/api/chat', { method: 'POST', body: JSON.stringify({ text, image_base64 }) })`. Базовый виджет ждёт полный JSON. Если реализован SSE — виджет читает `POST /chat/stream`, каналы по-прежнему вызывают `POST /chat`. Декодировать base64 обратно в файл на клиенте не нужно — бэкенд отдаёт готовый текстовый ответ.
  Тяжёлые скриншоты перед `toBase64` сжимать (canvas / `browser-image-compression`, ориентир 1024×768).

### 5.4. Тесты

- Отправка текста, получение ответа.
- Отправка изображения, получение ответа.
- Проверка, что при эскалации отображается корректное сообщение.
- Проверка отображения источников.

### 5.5. Критерий завершения

- Виджет работает без ошибок, интерфейс понятен пользователю.
- Основной сценарий (вопрос → ответ) проходит гладко.

## Этап 7. Интеграция с внешними каналами (упрощённо)

### 7.1. Цель

## 11. Риски и их смягчение

- **GigaChat API лимиты и время ответа**: classify — правила, не модель. Уверенность — скор ретривала, не второй вызов. Эмбеддинги запросов и повторяющиеся ответы — Redis (`kb_version` сбрасывает ответы при изменении БЗ). На вопрос по 1С без картинки — один generate. В виджете — индикатор загрузки; SSE — опционально отдельным маршрутом, не внутри `POST /chat`.
- **Бюджет задержки (текст, без картинки)**: приветствие / «спасибо» — меньше 100 мс; повтор вопроса при той же БЗ — меньше 200 мс из Redis; слабый поиск — эскалация без generate; новый вопрос — retrieve + один generate; скриншот — узкое место Vision, сжатие на клиенте (п. 3.5).
- **Сложность интеграции Bitrix/Redmine**: делать упрощённо, оставляя ядро на виджете.
- **Отсутствие данных для БЗ**: наполнить тестовыми данными из предоставленных источников (инструкции, документация 1С).
- **Две ORM на одной БД (Prisma + SQLAlchemy)**: жёстко разграничены по таблицам (auth vs домен), миграции не пересекаются; не давать Prisma-схеме трогать домен-таблицы и наоборот.

## 12. Известные пробелы (требуют внимания)

- **Нет realtime-оповещения оператора о новых эскалациях.** Список диалогов (`GET /api/conversations`, этап 6) на фронте (`chat-page.tsx`) подтягивается через React Query без `refetchInterval`, без WebSocket и без SSE. Инвалидация запроса `["conversations"]` происходит только когда сам оператор что-то отправляет (`chat-page.tsx:154`). Если оператор просто читает список, новая эскалация от гостя не появится сама — нужен либо ручной рефреш страницы, либо доработка:
  - самое дешёвое: `refetchInterval` на список диалогов (поллинг);
  - честный realtime: WebSocket или SSE-канал с бэкенда при создании `Escalation`.

  **Исправлено поллингом**: список диалогов автообновляется раз в 5 секунд (`refetchInterval: 5_000`), а `chatService` читает реальные `GET /api/conversations` и `GET /api/conversations/{id}`. Оператору достаточно держать панель открытой — новые эскалации появляются без ручного рефреша. Полноценный WebSocket/SSE остаётся возможным будущим улучшением.
