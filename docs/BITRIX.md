# Подключение Bitrix24: куда тыкать

Инструкция для живого портала (сейчас тестовый `b24-adkm07.bitrix24.ru`).
Секреты в этот файл не кладём — только имена переменных и клики.

Два входа, одно ядро агента. Кастомный коннектор **не удаляем**.

| Кто пишет | Куда тыкать | Что несёт |
| --- | --- | --- |
| Ты / жюри **как клиент** | Контакт-центр → линия → **Онлайн-чат** | Бот (`imbot`) |
| Сторонняя платформа | Своё приложение / API | Кастомный коннектор |
| Ты **как оператор** | Диалог линии / карточка сделки | Bitrix, бот молчит |

Кастомный коннектор **не даёт окна**, куда печатать как клиент. Сообщение
«Тестовый Клиент» / диалог с канбана сделок — это имитация через API, не
клиентский чат. Зелёная плитка **«Molvest AI Agent»** в контакт-центре —
тот же коннектор, не окно клиента.

`/health` = API жив. Ответ по 1С = ещё GigaChat + документы в базе знаний.
Пустая база почти всегда даёт эскалацию: вебхук **200**, в чате **тишина**.
Так задумано (порог уверенности), не баг канала.

## 0. Что должно быть запущено

На машине одновременно:

1. API на порту **8000** (Docker-контейнер `api` или `make api`).
2. Ngrok: `ngrok http 8000`.
3. Корневой `.env` с блоком `BITRIX_*` **и** ключом GigaChat.

Проверка API:

```bash
curl -sf http://localhost:8000/health
```

Должно вернуть `{"status":"ok"}`. Без этого Bitrix и ngrok бесполезны.

Чтобы агент **ответил текстом**, а не только принял событие:

| Нужно | Зачем |
| --- | --- |
| `GIGACHAT_API_KEY` | Генерация ответа |
| Документы в админке / проиндексированная база | Иначе уверенность низкая → бот молчит |
| `BITRIX_PORTAL_URL` = хост этого портала | Иначе входящие **403** (домен не совпал) |
| `BITRIX_APP_USER_ID` + `BITRIX_APP_TOKEN` | Без них установка проходит, бот **не регистрируется** и ответ не уходит |
| `BITRIX_CLIENT_ID` + `BITRIX_CLIENT_SECRET` | Обновление OAuth (~час). Без них ответы со временем отвалятся |

Режим `OPERATOR_ASSIST_MODE` по умолчанию `auto`: бот отвечает гостю
и после эскалации, если уверенность не ниже порога. Для черновика
оператору без автоответа после эскалации поставь `draft`.

Логи API (почему бот не зарегистрировался / ответ не ушёл):

```bash
docker compose logs -f api
```

Ищи: `bitrix ol bot готов`, `бот открытой линии не зарегистрирован`,
`ответ бота не доставлен`, `ol_bot эскалация`.

## 1. Ngrok — каждый раз, когда поднимаешь демо

Bitrix не ходит на `localhost`. Нужен публичный HTTPS.

### 1.1. Запуск

В отдельном терминале, из любой папки:

```bash
ngrok http 8000
```

Не глуши этот терминал, пока крутишь Bitrix.

### 1.2. Где взять URL

В окне ngrok строка **Forwarding** — адрес вида
`https://что-то.ngrok-free.dev`.

Либо браузер: [http://127.0.0.1:4040](http://127.0.0.1:4040) → тот же https.

### 1.3. Прописать в `.env`

Корень репозитория, файл `.env` (не `.env.example`):

```bash
BITRIX_HANDLER_BASE_URL=https://<твой-ngrok-без-слэша-в-конце>
BITRIX_BOT_CODE=molvest_support
```

`BITRIX_APPLICATION_TOKEN` — отдельное поле, см. § 3.4.

Порядок важен: сначала `.env` и пересоздание API, **потом** «Переустановить».
Иначе Bitrix зарегистрирует бота на пустой или старый URL.

### 1.4. Пересоздать контейнер API

Обычный `docker compose restart` **не** перечитывает `.env`. Нужно:

```bash
docker compose up -d --force-recreate api
```

Подожди 5–10 секунд, снова `curl` на `/health`.

`make restart` тоже не подхватывает новые переменные — тот же `--force-recreate`.

### 1.5. Если перезапустил ngrok

На бесплатном плане URL **меняется**. Тогда заново:

1. новый URL → `BITRIX_HANDLER_BASE_URL`;
2. пересоздать `api`;
3. в карточке приложения Bitrix обновить оба пути (§ 3.2);
4. **удалить** старого бота «Молвест поддержка» на портале (если он уже есть);
5. **Переустановить** приложение.

Повторная установка **не меняет** URL событий у уже существующего бота
с кодом `molvest_support` — код нарочно переиспользует его, чтобы не плодить
дубли. Старый ngrok в обработчике бота так и останется мёртвым, пока бота
не удалить и не дать установке создать его заново.

Старый ngrok-хост в карточке приложения тоже больше не работает.

## 2. Куда не тыкать (частая путаница)

Эти экраны **не** являются клиентским онлайн-чатом:

| Экран | Зачем он | Это не чат клиента |
| --- | --- | --- |
| CRM → Сделки (канбан) | Воронка. Карточка «Тестовый Клиент» — след коннектора | Нет |
| Пузырь чата **справа** (узкая панель) | Внутренний мессенджер сотрудников | Нет |
| «Онлайн-запись» в левом меню | Запись на услуги, другой модуль | Нет |
| Приложения → список интеграций (`/devops/list/`) | Список локальных приложений | Нет |
| Карточка «Локальное приложение» (`/devops/edit/application/…`) | Права и URL вебхуков | Нет |
| Зелёная плитка коннектора в контакт-центре | Внешний канал, не виджет | Нет |

Онлайн-чат живёт в **Контакт-центре**, § 5.

Импровизированный `POST /webhook/bitrix` (сценарий 2, внутренний токен) —
другой контур, эта инструкция его не настраивает.

## 3. Локальное приложение — права и URL

Нужна карточка **того** серверного приложения, чей `client_id` уже стоит в
`.env` как `BITRIX_CLIENT_ID`. На портале может быть несколько «Локальное
приложение» — открывай то, где в правах уже есть открытые линии и
коннекторы, не пустышку только с CRM.

### 3.1. Как открыть карточку

Вариант А (поиск):

1. Вверху страница — поле поиска с подписью **«Битрикс 24»**.
2. Набери: `разработчик` или `интеграции` или `локальное приложение`.
3. Открой **Интеграции** / **Разработчикам**.

Вариант Б (меню):

1. Слева внизу **Настройки** (шестерёнка).
2. Дальше раздел вроде **Настройки** → **Разработчикам** → **Интеграции**.
3. Или прямой путь в адресной строке: `https://<портал>/devops/list/`.

В таблице клик по нужному приложению (или карандаш) → форма редактирования
`/devops/edit/application/<id>/`.

Тип: **Серверное**. Галка «Приложение само завершает установку» — **снята**.
Иначе Bitrix не пришлёт токены, install вернёт **422**.

### 3.2. Два URL (подставь текущий ngrok)

| Поле на форме | Что вписать |
| --- | --- |
| **Путь для первоначальной установки** | `https://<ngrok>/webhook/bitrix/install` |
| **Путь вашего обработчика** | `https://<ngrok>/webhook/bitrix/openlines` |

Обработчик `/openlines` — это коннектор, так и должно быть. Бот вешается сам
при установке на `/webhook/bitrix/bot`, это поле на форме не ищи.

Смена ngrok в этих двух полях **не** обновляет обработчик уже созданного бота
(см. § 1.5).

### 3.3. Права — блок «Настройка прав»

Нажимай **«+ выбрать»** и добавь, если ещё нет:

| Как подписано в списке | Код | Зачем |
| --- | --- | --- |
| Коннекторы для внешних мессенджеров | `imconnector` | Коннектор |
| Открытые линии | `imopenlines` | Линия |
| Чат и уведомления | `im` | Чаты |
| Диск | `disk` | Вложения |
| Встраивание приложений | `placement` | Регистрация коннектора |
| **Создание и управление чат-ботами** | **`imbot`** | **Бот. Без этого онлайн-чат с агентом не взлетит** |

«Чат и уведомления (`im`)» **не заменяет** `imbot`. Если в чипсах прав нет
слова про чат-ботов — добавь.

Внизу формы: **Сохранить**.

Потом синяя кнопка **«ПЕРЕУСТАНОВИТЬ»** на этой же странице. Смена прав
без переустановки **не действует**: старый OAuth-токен новые права не
получает.

После клика в ngrok (страница 4040) должен появиться:

`POST /webhook/bitrix/install` → **200**.

Открой этот запрос → тело → `auth[scope]`. В строке должно быть **`imbot`**.
Если его нет — в карточке права не сохранились, бот не зарегистрируется
(`insufficient_scope` в логе API).

Если 422 — Bitrix не донёс токены установки; проверь, что галка
«само завершает установку» снята и путь install указывает на живой ngrok.

Install **200** ≠ бот создан. В логе API после установки должно быть
`bitrix ol bot готов`. Warning про пустой handler / REST / ошибку API —
бота нет, коннектор при этом может жить.

### 3.4. Откуда `BITRIX_APPLICATION_TOKEN`

Это **не** «Ключ приложения» (`client_secret`) и **не** `BITRIX_APP_TOKEN`.
Три разные строки.

1. Открой [http://127.0.0.1:4040](http://127.0.0.1:4040).
2. Слева список запросов → последний успешный **`POST /webhook/bitrix/install`**.
3. Тело (form) → поле **`auth[application_token]`**.
4. Вставь в `.env` в `BITRIX_APPLICATION_TOKEN=`.
5. Снова `docker compose up -d --force-recreate api`.

Пустой токен **или** пустой `BITRIX_PORTAL_URL` → все входящие события
с портала получают **403**.

Хост в `BITRIX_PORTAL_URL` должен совпасть с доменом портала
(`b24-adkm07.bitrix24.ru`, без пути и без лишнего www). Иначе тоже **403**,
даже при верном токене.

Переустановка приложения обычно **не** меняет `application_token`. Меняет
OAuth `access_token` / `refresh_token` (их хранит база, в `.env` не кладём).

## 4. Контакт-центр — как туда попасть

Это **не** левый пункт «Онлайн-запись».

### Вариант А — поиск (самый надёжный)

1. Верхнее поле **«Битрикс 24»**.
2. Набери: `контакт-центр` или `контакт центр` или `open lines`.
3. Открой **Контакт-центр**.

### Вариант Б — через CRM

1. Слева пункт **CRM** (сейчас он подсвечен, если ты в сделках).
2. Вверху рабочей области CRM ищи вкладки/ещё: **Клиенты**.
3. Внутри клиентов: **Контакт-центр**.

Если пункта нет: шестерёнка слева **Настройки** → поиск по настройкам
«контакт-центр». На маленьком тарифе модуль может называться
**«Открытые линии»**.

Адрес часто такой: `https://<портал>/contact_center/` или
`/crm/contact_center/`.

## 5. Включить онлайн-чат и посадить бота

Цель: канал **Онлайн-чат** на **той же линии**, что `BITRIX_LINE_ID`
(у нас `1`). Имя линии любое — важен числовой id в настройках линии
(часто в URL или блоке «идентификатор»).

### 5.1. Выбрать линию

В контакт-центре:

1. Блок / список **открытых линий** (иногда «Каналы», «Открытые линии»).
2. Открой линию с номером **1** (или ту, чей id стоит в `.env`).

Если линий нет — «создать открытую линию», запомнить id, прописать в
`BITRIX_LINE_ID`, пересоздать API.

### 5.2. Канал «Онлайн-чат»

Внутри линии:

1. Список каналов (WhatsApp, Telegram, **Онлайн-чат**, коннекторы…).
2. Найди **Онлайн-чат** (иногда «Живой чат», «Чат на сайте», Live Chat).
3. Включи / подключи / «добавить канал».
4. В настройках виджета задай публичный адрес (код вроде `test`) и **Сохрани**.

Кастомный коннектор `molvest_ai_agent` в этом списке тоже может быть —
**не удаляй**. Он для внешних систем. Клиенту для ТЗ нужен именно
**Онлайн-чат**.

### 5.3. Очередь: бот первым

В настройках **той же линии** (не канала):

1. Раздел вроде **Очередь**, **Ответственные**, **Боты**.
2. Добавь бота **Молвест поддержка** или код `molvest_support`.
3. Поставь его **первым**, чтобы он отвечал до живого оператора.

Если в очереди только человек (например «Иван Климов») — сообщение
забирает оператор, в ngrok **не будет** `POST /webhook/bitrix/bot`.

Если бота в списке нет — установка с `imbot` не прошла. Вернись к § 3.3
и переустанови приложение, глядя на ngrok (install 200) **и** лог API.
В логах при пустом `BITRIX_HANDLER_BASE_URL` или без исходящего вебхука
(`BITRIX_APP_USER_ID` / `BITRIX_APP_TOKEN`) бот не регистрируется.

### 5.4. Открыть окно клиента — куда писать

Готовая ссылка после сохранения виджета:

`https://<портал>/online/<код>`

На тестовом портале это часто `https://b24-adkm07.bitrix24.ru/online/test`.

В настройках канала **Онлайн-чат** то же самое ищут как:

- «Открыть чат»
- «Публичная ссылка»
- «Страница чата»
- «Код виджета» → отдельная кнопка предпросмотра

Открой эту ссылку **в инкогнито** (чтобы не сесть в кресло оператора).

**Это и есть окно, куда печатать как клиент.** Пиши обычный вопрос по 1С,
который есть в базе знаний. Жди ответ в **этом же** окне.

В инспекторе ngrok должен появиться:

`POST /webhook/bitrix/bot` → **200**.

200 без текста в чате — смотри лог API: эскалация, нет `bot_id`, нет OAuth,
REST не сконфигурирован. Клиенту при эскалации мы **ничего** не пишем.
Черновик уходит в консоль (`/operator`, поле подсказки) и оператору портала
как личное уведомление (`im.notify` на `BITRIX_APP_USER_ID`), не в окно гостя.

После эскалации в режиме `draft` следующие реплики гостя тоже без автоответа:
обновляется черновик. Для демо «написал → бот ответил» ставь
`OPERATOR_ASSIST_MODE=auto`.

Скриншот PNG/JPEG в том же окне идёт в vision (прямой URL или file id диска).

## 6. Где смотреть диалог как оператор

Это уже не клиентское окно.

1. Снова **Контакт-центр** → вкладка вроде **Список диалогов** /
   **Открытые линии** → диалоги.
2. Либо канбан CRM: карточка сделки с чатиком (как «Тестовый Клиент») —
   иконка сообщения на карточке открывает диалог **оператора**.
3. Пузырь **справа** может показать тот же диалог, если линия привязана
   к мессенджеру — но писать туда «как клиент» нельзя.

Если уверенность агента низкая, бот **молчит** гостю, черновик — в `/operator`
и в уведомлении оператору. Диалог забирает человек здесь.

## 7. Два потока в одной картинке

```
Клиент (онлайн-чат Bitrix)          ← это окно ТЗ / жюри
    → POST /webhook/bitrix/bot
    → агент (база знаний)
    → imbot.message.add
    → ответ в том же чате

Внешняя система                    ← коннектор, окна клиента нет
    → Bitrix принимает сообщение
    → POST /webhook/bitrix/openlines
    → агент
    → imconnector.send.messages
    → реплика в диалоге у оператора

Имитация «как будто клиент» (curl / скрипт)
    → сразу imconnector.send.messages
    → появляется «Тестовый Клиент» на канбане
    → это не онлайн-чат и не проверка бота
```

Не путать исходящие методы: бот отвечает через `imbot.message.add`.
`imconnector.send.messages` на пути бота не вызывается.

## 8. Чеклист «всё живое»

1. `curl -sf http://localhost:8000/health` → ok.
2. Ngrok 4040 online, хост = `BITRIX_HANDLER_BASE_URL` (без `/` на конце).
3. В карточке приложения есть **`imbot`**, пути с **текущим** ngrok.
4. После «Переустановить»: `POST /webhook/bitrix/install` → 200,
   в теле `auth[scope]` есть `imbot`.
5. В логе API: `bitrix ol bot готов` (не warning про handler/REST).
6. `BITRIX_APPLICATION_TOKEN` не пустой, хост портала совпадает, API пересоздан.
7. Контакт-центр → линия из `BITRIX_LINE_ID` → онлайн-чат включён,
   бот **первым** в очереди.
8. Есть ключ GigaChat и хотя бы один проиндексированный документ.
9. Открыл `https://<портал>/online/<код>` в инкогнито, написал вопрос из базы
   → `POST /webhook/bitrix/bot` → 200 → ответ **в том же** окне.

## 9. Если не отвечает

| Что видишь | Куда тыкать / что чинить |
| --- | --- |
| Не знаешь, где чат | Не CRM-канбан. Поиск → **контакт-центр** → линия → онлайн-чат → `/online/…` |
| Пишешь в пузырь справа | Это чат сотрудников. Клиенту — ссылка онлайн-чата линии |
| Зелёная плитка коннектора | Это не виджет. Клиенту — канал «Онлайн-чат» |
| В ngrok нет `/webhook/bitrix/bot` | Не то окно, бот не в очереди, нет `imbot`, или у бота старый ngrok (§ 1.5) |
| `/webhook/bitrix/bot` → **403** | Пустой/чужой `BITRIX_APPLICATION_TOKEN`, API не пересоздали, или хост `BITRIX_PORTAL_URL` ≠ домен портала |
| `/webhook/bitrix/bot` → **200**, в чате тишина | Эскалация (пустая база / слабый матч), нет OAuth/`bot_id`, нет `BITRIX_APP_*`. Смотри `docker compose logs api` |
| Install 200, бота нет в очереди | Нет `imbot` в `auth[scope]`, пустой handler на момент установки, нет `BITRIX_APP_USER_ID`/`TOKEN` |
| 404 на install/bot | Ngrok не на 8000, API лёг, в карточке старый URL |
| Ngrok сменил хост | § 1.5 целиком, включая **удаление** старого бота |
| Первый ответ был, потом тишина | Диалог уже `escalated` при `draft`, или вопрос вне базы |
| 409 | Диалог в нашей БД уже закрыт — новое инкогнито-окно |

## 10. Переменные `.env` (имена)

| Переменная | Смысл | Кому нужна |
| --- | --- | --- |
| `BITRIX_PORTAL_URL` | `https://….bitrix24.ru` (только хост портала) | Оба входа |
| `BITRIX_LINE_ID` | id линии (у нас `1`) | Очередь и коннектор |
| `BITRIX_CONNECTOR_ID` | код коннектора | Только коннектор |
| `BITRIX_CLIENT_ID` / `BITRIX_CLIENT_SECRET` | с карточки приложения | OAuth (оба исходящих REST) |
| `BITRIX_APP_USER_ID` / `BITRIX_APP_TOKEN` | исходящий REST-вебхук `/rest/…` | Сборка REST-клиента; без них бот не регистрируется |
| `BITRIX_APPLICATION_TOKEN` | `auth[application_token]` из install | Входящие `/bot` и `/openlines` |
| `BITRIX_HANDLER_BASE_URL` | https ngrok без хвоста | Регистрация бота |
| `BITRIX_BOT_CODE` | `molvest_support` | Регистрация бота |

Не путать ключ приложения, токен исходящего вебхука и
`BITRIX_APPLICATION_TOKEN` — это три разных строки.

Access/refresh OAuth в `.env` не кладём: их пишет
`POST /webhook/bitrix/install` в таблицу `bitrix_oauth_tokens`.

> [!WARNING]
> `POST /webhook/bitrix/install` не проверяет подпись или секрет запроса —
> он принимает любой POST с правдоподобными полями `auth[access_token]`,
> `auth[refresh_token]`, `auth[expires_in]`, `auth[member_id]` и
> перезаписывает сохранённые OAuth-токены для этого `member_id`.
> Единственный барьер — секретность `BITRIX_HANDLER_BASE_URL` (ngrok).
> Приемлемо для демо/хакатонного install-флоу за приватным URL, но не
> публикуйте этот URL там, где его может подобрать посторонний — так он
> сможет перехватить токен портала.

Коннектор для сторонних платформ после этой инструкции не трогай: он
уже рядом и должен остаться.
