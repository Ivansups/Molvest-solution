## Context

На защите закрываем пробелы ТЗ/переписки #2, #6, #7, #8, #1, #3.
Каналы Bitrix/Redmine уже живут; ядро — `run_chat_turn` + LangGraph.
Путаница в режимах: `operator_assist_mode` (`draft`/`auto`) влияет
только **после** эскалации, а подписи в `/settings` это скрывают.
Заказчик просит режим «ИИ не пишет гостю, пока оператор не подтвердит».

Инварианты: статус только через `transition_status`; порог — одна
константа; канальная специфика в `channels/`; граф не знает канал;
GigaChat только через `core/`; логика в `services/`.

## Goals / Non-Goals

**Goals:**

- Одна ось режимов: `auto` | `draft` | `agent` без второго флага.
  Значение настройки `agent` = каждый ответ ИИ — черновик до «Отправить».
- Шлюз выдачи гостю в `services/`, общий для виджета, Bitrix, Redmine.
- Кнопка «Позвать оператора» + `force_handoff` на `POST /chat`.
- PATCH title/metadata документа без реиндекса.
- Точки «печатает», инлайн-цитата ~200 символов, id диалога в
  sessionStorage + localStorage.
- `docs/OPS.md`.
- Модалка закрытия у оператора с сохранением подтверждения.

**Non-Goals:**

- Grafana, SSE, облако, обучение на кейсах, доменная БЗ.
- Гостевой CSAT в Bitrix/Redmine.
- Двухосевая матрица «когда слать» × «что видит оператор».
- Смена дефолта: по-прежнему `draft`.
- Подстановка текста в поле ввода Bitrix.

## Decisions

### D1. Три значения одного поля, не boolean сверху

`operator_assist_mode: Literal["draft", "auto", "agent"]`.
Env `OPERATOR_ASSIST_MODE`, runtime override, `GET`/`PUT /api/settings`.

| Режим | Первый ход `open`, скор ≥ порога | После `escalated` |
| --- | --- | --- |
| `auto` | ответ гостю | снова граф, автоответ если скор ок |
| `draft` | ответ гостю | hold: виджет без generate; канал — `generate_draft` |
| `agent` | generate → черновик → эскалация, гостю не слать | как каналный `draft`: обновлять черновик |

Значение `agent` — режим `operator_assist_mode`, не LangGraph-агент:
каждый ответ ИИ ждёт «Отправить» оператора.

Альтернатива «`require_operator_confirm` + старые draft/auto» отклонена:
четыре комбинации, из них две бессмысленны, UI на защите разъедется.
Двухосевая модель точнее сценария 2, но для хакатона один селект.

Копирайт `/settings` переписать по таблице, не по внутренним именам.

### D2. Шлюз выдачи — после графа, в `services/`

Новая функция рядом с `run_chat_turn` (например
`apply_operator_reply_policy`): смотрит эффективный режим и результат
графа, решает: слать гостю / эскалировать / положить текст в
`suggested_response`. Роутеры и `ol_bot` / `openlines` / `redmine`
не ветвят режим сами — они уже смотрят `ChatResponse.escalated`.

В режиме `agent` при готовом `answer` шлюз:

1. `open → escalated` через `transition_status`;
2. строка `Escalation` с причиной режима (не «слабый скор»);
3. `suggested_response = answer`;
4. гостевой текст ответа — фраза эскалации (виджет) / `escalated=true`
   без assistant-реплики;
5. generate уже был в графе — второй `generate_draft` не зовём.

Если граф сам эскалировал без ответа (скор, хэндофф): после commit
зовём существующий `fill_escalation_draft` **и для виджета** в
режиме `agent` (сегодня виджет черновик на первой эскалации не пишет).

`live_thread` / `should_draft_followup`: режим `agent` на уже
`escalated` или после `role=operator` идёт в ту же draft-ветку, что
`draft`. Первый `open` в режиме `agent` — через `run_chat_turn`.

Альтернатива «узел графа» отклонена: граф узнал бы о политике
оператора и канале. Альтернатива «флаг в каждом адаптере» — дыры.

### D3. `force_handoff` на контракте чата

`ChatRequest.force_handoff: bool = False`. Кнопка виджета шлёт
`true` и короткий текст («Позовите оператора»). Узел `handoff_detect`:
если флаг — сразу `intent=handoff`, `escalated=true`, причина явного
запроса, **без** OpenRouter/GigaChat. Пустой текст + флаг тоже
эскалация, не шаблон «опишите проблему».

Альтернатива «только NLP по тексту кнопки» отклонена: на защите
классификатор не должен быть единственной точкой.

### D4. PATCH документа без реиндекса

`PATCH /api/documents/{id}?installation_id=` JSON
`{ title?: str, metadata?: object }`. Меняет только title и
`extra_metadata`. Файл, чанки, `status`, `kb_version` не трогаем.
Пустое тело / оба поля отсутствуют — 422. Чужая установка — 404.
Форма карточки зовёт этот PATCH; `unsupportedEndpoint` убрать.

Категория и описание как сейчас живут в JSON metadata.

### D5. Id диалога: sessionStorage + localStorage, не URL

Пишем оба ключа `guest_conversation_id`. Читаем sessionStorage, если
пусто — localStorage. «Новый диалог» чистит оба. URL `?c=` не делаем:
UUID в истории и реферере, лишний роут, выигрыш только «кинуть ссылку».
Новая вкладка того же браузера продолжит чат — для демо это плюс.

### D6. UX виджета

Индикатор ожидания: оставить спиннер и текст, добавить три точки
(CSS, без новой библиотеки). Источник: название + обрезка
`chunk_text` ~200 символов сразу; клик по-прежнему раскрывает полный
текст.

### D7. Подтверждение закрытия — поля на Conversation

`POST /api/conversations/{id}/resolve`: `installation_id`,
`confirmed: true`, опционально `comment`. `confirmed=false` или нет
поля — 422, статус не меняется. «Нет» в модалке = отмена, запроса нет.

Колонки: `resolve_comment` (text, nullable), `resolve_confirmed_at`
(timestamptz, nullable). Отдельная таблица не нужна. Статус по-прежнему
только `transition_status`. Повторный resolve на уже `resolved` —
200 без второй записи. Комментарий не уходит гостю и не в Bitrix.

### D8. `docs/OPS.md`

Новый файл: переменные (имена, не секреты), `/health`, БЗ (включая
PATCH), настройки/режимы, куда смотреть каналы (ссылки на BITRIX.md /
REDMINE.md). README — одна ссылка. Не копировать Make/troubleshooting
из DEV.md.

## Risks / Trade-offs

- [В режиме `agent` каждый уверенный вопрос = эскалация + generate] →
  на защите переключают в `auto`/`draft` для демо Q&A; в OPS.md и
  настройках это явно.
- [`fill_escalation_draft` дважды посчитает generate] → если
  `suggested_response` уже заполнен шлюзом, helper не зовёт generate.
- [localStorage склеивает вкладки] → «Новый диалог» сбрасывает ключ;
  URL не вводим.
- [Старые клиенты settings без `agent`] → `draft`/`auto`
  принимают как раньше; третье значение опционально.
- [Модалка «нет» без записи] → для защиты достаточно; аудит отказа
  закрытия — потом.

## Migration Plan

1. Расширить Literal и валидатор env; дефолт `draft`.
2. Шлюз + тесты трёх режимов до UI.
3. `force_handoff`, PATCH, resolve body, миграция колонок.
4. Фронт: настройки, виджет, модалка, форма документа.
5. OPS.md + ссылка в README.
6. Откат: выставить `draft` или `auto`; неизвестный `agent` в
   старом процессе не появится — это новый код. Идентификатор третьего
   режима — `agent`; в проде не хранилось, миграции данных нет.
