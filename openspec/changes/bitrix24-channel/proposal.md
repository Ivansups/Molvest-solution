## Why

Сценарий 1 ТЗ («Q&A по базе знаний») закрыт только демо-виджетом: агент не
подключён к реальному порталу Bitrix24, и сообщение из открытой линии не
доходит до ядра и не получает ответ назад в тот же диалог. Существующий
`/webhook/bitrix` — импровизированный контур сценария 2 (live-тред, ключ
внутреннего сервиса, нет исходящего REST) и не работает против живого портала.
Нужна реальная интеграция Bitrix24: входящие события Open Lines с проверкой
токена приложения, маппинг id сессии открытой линии → `conversation_id`
(ROADMAP §14.2) и отправка ответа агента обратно в этот диалог.

## What Changes

- **Новый входящий контур реального портала**: webhook формата Open Lines
  Bitrix24 (входящее сообщение открытой линии: сессия/диалог, author id, текст,
  при наличии — файл/картинка) с проверкой токена приложения вместо ключа
  внутреннего сервиса; импровизированный `/webhook/bitrix` сценария 2 остаётся.
- **Маппинг «id диалога ОЛ → наш `conversation_id`»** (ROADMAP §14.2):
  переиспользуем механизм `ChannelThread` (или выделяем таблицу
  `bitrix_dialog_id` — решение в design). Повтор внешнего id диалога/сообщения
  не создаёт новый диалог и не гоняет граф повторно.
- **Исходящий ответ в тот же диалог**: после обработки ядром ответ агента
  отправляется обратно в открытую линию через REST Bitrix24
  (`imconnector.send.messages`); вызов REST — после фиксации состояния БД
  (инвариант: внешние вызовы не внутри бизнес-транзакции).
- **Переиспользование ядра**: та же логика, что `POST /chat`, через
  `run_chat_turn` с канальными полями `channel="bitrix"` /
  `channel_message_id` — без дублирования графа.
- **Конфигурация только через env**: `BITRIX_PORTAL_URL`, `BITRIX_APP_USER_ID`,
  `BITRIX_APP_CODE`/OAuth/webhook-токен — ничего в `/settings`, репо и логах.

## Capabilities

### New Capabilities

- `bitrix24-channel`: реальная интеграция портала Bitrix24 по сценарию 1 —
  приём и валидация входящих событий Open Lines, маппинг id диалога ОЛ →
  `conversation_id` с идемпотентностью повторов, отправка ответа агента в тот
  же диалог через REST, конфигурация из `BITRIX_*` env.

### Modified Capabilities

- (пусто: существующий битрикс-контур задан несинхронизированными дельтами
  `live-bitrix-thread-assist`, а не спецификациями в `openspec/specs/`; этот
  change добавляет новую capability, не меняя требований существующих specs)

## Impact

- `server/app/channels/bitrix/` — расширение пакета: REST-клиент Bitrix
  (`rest.py`), схемы реального формата событий, роутер webhook Open Lines.
- `server/app/services/` — оркестрация входящего события через `run_chat_turn`
  и маппинг диалога (по образцу `services/live_thread.py`).
- `server/app/models/` — таблица `bitrix_dialog_id` (если решено в design) +
  Alembic миграция; нативный маппинг `ChannelThread` — без изменений.
- `server/app/core/config.py`, `.env.example` — `BITRIX_*` переменные.
- `README.md` — раздел «Интеграция Bitrix24»: нужные env и права приложения
  (Open Lines, `imconnector`).
- Тесты: `server/tests/test_bitrix_channel.py` (валидация токена, маппинг,
  идемпотентность повтора id, исходящий REST-вызов, отсутствие секретов в
  ответах/логах).
- Вне scope: сценарий 2 на живом портале (таск #19 закрыт имитацией), Redmine,
  токены в `/settings`, обработка вложений вне поля текущего webhook.
