## Why

На защите остаются дыры ТЗ и переписки, которые уже не закрыть каналами:
гость не может явно позвать оператора кнопкой, документ нельзя поправить
без реиндекса, виджет и гайд эксплуатации слабее демо, а режимы
`draft`/`auto` не делают то, что просит заказчик — «каждый ответ ИИ
подтверждает человек». Сейчас первый уверенный ответ всё равно уходит
гостю; `draft` держит черновик только **после** эскалации. Нужен один
понятный переключатель, а не третий флаг поверх путаницы.

## What Changes

- **Режимы работы (переписка #1):** одно поле `operator_assist_mode` с
  тремя значениями: `auto` | `draft` | `agent`. Значение настройки
  `agent` — каждый ответ ИИ остаётся черновиком, пока оператор не
  нажмёт «Отправить» (это не LangGraph и не название продукта).
  Отдельный `require_operator_confirm` **не** вводим. Шлюз выдачи
  гостю — в `services/`, общий для виджета, Bitrix и Redmine. Граф
  канала не знает.
- **Позвать оператора (#2):** кнопка в гостевом виджете + опциональный
  `force_handoff` в `POST /chat`, чтобы хэндофф не зависел от NLP.
- **PATCH документа (#6):** `PATCH /api/documents/{id}` меняет title и
  metadata без реиндекса; форма в админке перестаёт звать заглушку.
- **UX виджета (#7):** классические точки «печатает»; ~200 символов
  цитаты источника сразу; `conversation_id` ещё и в `localStorage`
  (sessionStorage оставляем).
- **Эксплуатация (#8):** `docs/OPS.md` (env, health, БЗ, каналы);
  README по-прежнему только про старт.
- **Подтверждение закрытия (#3):** модалка оператора «решено? да/нет» и
  опциональный комментарий **до** `resolved`. Гостевой CSAT в
  Bitrix/Redmine — вне scope.

## Режимы: план ТЗ vs код vs модель этого change

### Что планировали документы

| Источник | Смысл |
| --- | --- |
| Сценарий 1 (`SCENARIOS.md`) | Порог ~80%: выше — ответ гостю, ниже — эскалация + черновик оператору |
| Сценарий 2 | Два выхода **уже идущего** чата оператор↔гость: `draft` (человек подтверждает) и `auto` (ответ сразу гостю) |
| ROADMAP / settings | `OPERATOR_ASSIST_MODE=draft\|auto`; порог и режим в панели |
| Переписка заказчика | Нужен режим «все ответы ИИ — черновик, пока оператор не подтвердит», с выключателем |

### Что в коде сейчас

`draft` и `auto` меняют поведение **только после** `Conversation.status=escalated`
(и иногда после реплики `role=operator` на канале). Первый ход с скором ≥
порога всегда уходит гостю. Подписи в `/settings` врут: «draft — черновик
только по запросу оператора» — на каналах черновик пишется сам; «auto —
агент может ответить гостю после эскалации» — про первую реплику молчит.

### Модель дальше (одна ось, без второго флага)

| Режим | Гость видит сырой ответ ИИ? | Оператор |
| --- | --- | --- |
| `auto` | Да, если скор ≥ порога; иначе эскалация | После эскалации следующие реплики гостя снова могут уйти автоответом |
| `draft` (как сейчас, дефолт) | Да, пока диалог `open`; после эскалации — нет | Черновики после эскалации (канал заполняет сам; виджет — кнопка «Сгенерировать») |
| `agent` (новый; значение настройки) | Никогда, пока оператор не нажмёт «Отправить» | Каждый сгенерированный ответ — `suggested_response`; диалог эскалируется |

Значение `agent` — режим настроек, не LangGraph-агент: ИИ никогда не
пишет сырой ответ гостю, пока оператор не нажмёт «Отправить».

Миграция: значения `auto`/`draft` в env и `PUT /api/settings` не меняют
смысл. Неизвестное значение — как сейчас, отклонение схемой.
Идентификатор третьего режима — `agent`, не `confirm_all`; в проде
старого значения нет, миграции данных нет. Копирайт настроек
переписать. Порог уверенности остаётся **одной** константой.

## Capabilities

### New Capabilities

- `ops-runbook`: гайд эксплуатации `docs/OPS.md` (env, health, БЗ, каналы),
  без дубля инструкции запуска из README.
- `resolve-confirmation`: перед `escalated → resolved` оператор явно
  отвечает «решено? да/нет» и может оставить комментарий; факт
  сохраняется. Только консоль, не CSAT гостя.

### Modified Capabilities

- `operator-assist`: третье значение настройки `agent`; шлюз выдачи в
  `services/`; Send по-прежнему единственный путь сырого ответа гостю в
  режиме `agent`.
- `agent-runtime-settings`: `operator_assist_mode` принимает `agent`;
  UI показывает три понятных режима (`auto` / `draft` / `agent`).
- `guest-chat-ui`: кнопка «Позвать оператора», точки печати, инлайн-цитата
  источника, устойчивость id диалога.
- `knowledge-base-documents`: PATCH title+metadata без реиндекса.
- `conversation-records`: `force_handoff`; в режиме `agent` ответ ИИ в
  черновик, не в ленту гостя; поля подтверждения закрытия.
- `agent-dialog-graph`: `force_handoff=true` эскалирует без классификатора.
- `support-console-ui`: подписи режимов; модалка закрытия.
- `bitrix-escalation-handoff`: режим `agent` на канале = тишина гостю +
  черновик даже при скоре выше порога.
- `bitrix-live-portal-assist`: режим `agent` на follow-up после оператора —
  только черновик, не автоответ.
- `redmine-helpdesk`: тот же шлюз, что виджет и Bitrix.

## Impact

- `runtime_settings`, `config`, `GET`/`PUT /api/settings`, страница
  `/settings`.
- `run_chat_turn` / новый шлюз в `services/` (не роутеры, не `agent/`).
- `ChatRequest.force_handoff`; граф читает флаг, канал не знает.
- `PATCH /api/documents/{id}` + форма `knowledge-document-page`.
- Виджет `/chat`: кнопка, индикатор, источники, `localStorage`.
- `POST /api/conversations/{id}/resolve` + модалка `/operator` и
  `/chat/support`.
- `docs/OPS.md`; ссылка из README; BITRIX/REDMINE не дублировать целиком.
- Тесты: три режима, `force_handoff`, PATCH, resolve с/без подтверждения;
  регрессия `auto`/`draft` и каналов.
- Вне scope: Grafana, SSE, облако, обучение на кейсах, доменная БЗ,
  гостевой CSAT в Bitrix/Redmine, пункты ТЗ #4, #5, #9–#13.
