## Context

Case learning (`server/app/services/case_learning.py`, PR #46)
задокументирован как fail-closed: документ попадает в БЗ только при GOOD-
вердикте и успешной индексации, а транзиентная ошибка должна оставлять
диалог непомеченным, чтобы следующий `resolve` повторил попытку. По коду это
верно для вызова OpenRouter (`OpenRouterError` → ранний `return`, метка не
ставится), но не для шага индексации: `_ingest_case` глотает `IngestionError`
внутри себя и возвращается, а вызывающий код (`evaluate_and_ingest`) затем
безусловно вызывает `_mark_ingested`. Ошибка индексации со стороны диалога
выглядит неотличимо от "успешно инжестировано" — кейс теряется навсегда.

Остальная часть изменения — только документация: закрытие разрывов между тем,
что доки подразумевают, и тем, что код реально делает, найденных в ходе
ручного аудита.

## Goals / Non-Goals

**Goals:**
- Сделать ошибку индексации при инжесте кейса повторяемой на следующем
  `resolve`, приведя поведение в соответствие с задокументированным
  fail-closed контрактом.
- Сделать явными и точными в доках: порог RAG, тихий no-op без OpenRouter,
  границу "не решение оператора", покрытие CI моками, посадочную позицию по
  безопасности демо (`INTERNAL_SERVICE_TOKEN`, креды БД, install-эндпоинт
  Bitrix) — чтобы не вводить в заблуждение будущего читателя или оператора.

**Non-Goals:**
- Не добавлять аутентификацию в install-эндпоинт Bitrix. Он помечается как
  известный пробел; починка (HMAC/token-проверка против
  `BITRIX_APPLICATION_TOKEN`) — отдельное изменение, если/когда это выйдет
  за пределы демо за приватным ngrok.
- Не менять семантику ретраев сверх "не помечать разобранным при ошибке
  индексации" — без нового счётчика попыток, без backoff, без
  dead-letter-обработки. По-настоящему постоянная ошибка (например,
  некорректные данные чанка) будет повторяться на каждом `resolve` уже
  решённого диалога вечно; это совпадает с существующим поведением при
  ошибке OpenRouter и признаётся приемлемым при текущем масштабе (`resolve`
  не вызывается автоматически повторно для уже решённого диалога, кроме как
  этой же фоновой задачей, которая ни разу не завершилась успехом).
- Не менять семантику или дефолтное значение `CONFIDENCE_THRESHOLD` — только
  текст, который его описывает.

## Decisions

- **Сигнализировать об ошибке индексации через возвращаемое значение, а не
  повторный re-raise исключения.** `_ingest_case` возвращает `bool` (`True` =
  проиндексировано и закоммичено, `False` = ошибка и откат);
  `evaluate_and_ingest` вызывает `_mark_ingested` только когда `_ingest_case`
  вернул `True`. Рассмотренная альтернатива: пропустить `IngestionError`
  наружу из `_ingest_case` и поймать её в `evaluate_and_ingest`. Отклонено,
  потому что `_ingest_case` и так должен выполнить очистку
  (`session.delete(document)` + `commit`) в except-блоке перед выходом, так
  что re-raise после очистки не добавляет ясности по сравнению с булевым
  значением, но заставляет добавить лишний try/except в вызывающем коде без
  выигрыша в поведении.
- **Изменения в доках остаются только текстом, без новых спек-дельт.** Ни
  одна из правок в доках не меняет внешне наблюдаемые требования — порог RAG
  так же гейтит ответы, отсутствие OpenRouter так же пропускает шаг,
  реальное поведение install-эндпоинта Bitrix не меняется. Поэтому это
  оформляется как дополнение к существующим докам рядом с case learning (у
  PR #46 нет собственной спек-возможности `case-learning` — он был выпущен
  без неё), а не как файлы спек-дельт. Единственное исключение —
  `service-to-service-auth`, на неё только ссылаемся для контекста, не
  меняем.

## Risks / Trade-offs

- [Фикс маркировки может привести к тому, что перманентно сломанный диалог
  будет повторять попытку индексации при каждом будущем `resolve`] →
  Приемлемо: `resolve` для уже `RESOLVED` диалога — no-op по статусу, и этот
  путь ограничен тем, как часто к этому диалогу вообще возвращаются;
  совпадает с существующим прецедентом ошибки OpenRouter. Если это станет
  реальной проблемой — добавить лимит попыток отдельным изменением.
- [Переформулировка "только GigaChat" в "мультипровайдерность — это
  нормально" может читаться как откат заявленного требования] → Митигация:
  сослаться прямо на ТЗ (оно не требует единственного вендора), а не
  утверждать это голословно, чтобы правка в доках была проверяемой, а не
  просто успокаивающей.

## Migration Plan

- Фикс кода идёт обычным PR: изменить тип возврата `_ingest_case`, обновить
  `evaluate_and_ingest`, добавить регрессионный тест, что
  `case_ingested_at is None` после принудительной `IngestionError`.
  Миграция схемы или конфига не нужна. Откат не требует внимания — поведение
  становится только консервативнее (меньше ложных пометок "готово").
- Доки идут тем же PR (небольшие, низкий риск, ревьюятся вместе по списку
  файлов из proposal).
