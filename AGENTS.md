# Molvest AI-Agent — Agent Guide

Single source of truth for all AI agents (Cursor, Codex, Aider, Claude, …).

AI-агент техподдержки 1С для АО «Молвест»: Q&A по базе знаний (RAG), пассивное
подключение к чату оператора, анализ скриншотов ошибок 1С, управление базой
знаний. GigaChat — обязательное содержательное ядро решения (см.
`docs/technical spec/`, `docs/SCENARIOS.md`).

## Tech Stack

- Python ≥ 3.12, FastAPI (async), SQLAlchemy 2.x (async) + Alembic, Pydantic v2
- LangGraph — оркестрация диалогового графа агента
- PostgreSQL + `pgvector` — хранилище чанков базы знаний и векторный поиск
- GigaChat API — единственная LLM в решении
- React (Next.js, App Router) + Tailwind — админ-панель и демо-виджет чата
- Package manager: **uv** для Python (`uv run ...`, `uv add ...`), **pnpm** для
  Node — никогда `pip`, `poetry`, `npm`, `yarn`

## Organization Rules

- **Бизнес-логика → `services/`**, не во view/роутерах и не в моделях.
- **API** → FastAPI роутеры + `schemas.py` (Pydantic); один ресурс — один файл.
- **Чтение → `selectors.py`**; изменение состояния → `services/`.
- **Каналы (Bitrix24/email/web)** → вся специфика протокола живёт в
  `channels/<канал>/`, наружу отдаётся единый внутренний формат сообщения.
  Ядро агента (`agent/`) не знает, из какого канала пришёл запрос.
- **Вызовы GigaChat** — только через единый клиент в `core/`, не напрямую
  через `httpx`/`requests` в разных местах.
- Одна ответственность на файл; домены не лезут друг в друга напрямую —
  взаимодействие через services, а не прямой доступ к чужим моделям.
- **SRP на уровне классов**: один класс — одна ответственность, один повод для
  изменения. Мягкий порог — класс крупнее ~100 строк или с ~5+ публичными
  методами — сигнал разделить, а не жёсткое правило. Слои не смешивать: логика
  в services, данные — в models/schemas. Композиция предпочтительнее
  наследования. Не переусложнять: 3-строчный класс-обёртка, которая просто
  прокидывает вызов дальше, не нужен.

## Code Style

- **Язык**: идентификаторы — на английском; код-комментарии, докстринги и
  пояснения — **на русском**.
- **Типы** на каждом параметре и возвращаемом значении. Без `Any`, если это
  не оправдано (обосновать комментарием). Без wildcard-импортов.
- **Длина строки ≤ 88** (Ruff default).
- **Async** для всего I/O (FastAPI, LangGraph, вызовы GigaChat, retrieval).
- **Докстринги** на публичных функциях/классах. Комментарий — только на
  неочевидное "почему", никогда не пересказывает код.
- Самодокументируемые имена; чистые функции и неизменяемость где практично.

## Business Invariants (non-negotiable)

- **`Conversation.status`** (`open` → `escalated` → `resolved`) меняется только
  через центральный сервис перехода — никогда не присваивается напрямую из
  роутера, канального адаптера или узла графа.
- **Порог уверенности** (эскалация на оператора) — одна константа в конфиге,
  не захардкожена по сценариям.
- **Реиндексация документа атомарна**: старые чанки этого документа удаляются
  и новые вставляются в одной транзакции — retrieval никогда не видит
  наполовину обновлённый документ.
- **Изменение состояния диалога + запись в audit/лог эскалации** — в одной
  `transaction` (или эквиваленте на уровне сессии SQLAlchemy). При ошибке всё
  откатывается вместе.
- **Время** — в UTC, наружу отдаётся ISO 8601 с таймзоной.
- **Миграции явные** (Alembic); индексы и constraint'ы именуются понятно и
  единообразно (например `ix_<table>_<column>`, `uq_<table>_<column>`), а не
  оставляются с автосгенерированными именами.
- **Токены GigaChat и секреты каналов** — только через переменные окружения,
  никогда не коммитятся и не логируются.
- Внешние вызовы (GigaChat, Bitrix24, отправка email) — не внутри
  бизнес-транзакции БД; сначала фиксируем состояние, потом дёргаем внешний API.

## Minimalism — Do Not Write Extra Code

- **YAGNI**: делаем только то, что нужно для текущей задачи/сценария.
  Никакого "может пригодится потом".
- Не плодим абстракции/обёртки/конфиг-опции, которые сейчас не используются.
- Правим существующий код, а не дублируем; переиспользование раньше создания.
- Минимальный диф — не рефакторим нетронутый код без явной просьбы.
- Не добавляем error handling/логирование/фоллбеки для случаев, которые
  здесь не могут произойти.
- Если есть более простое решение — используем его, альтернативу упоминаем
  одной строкой.

## Code Quality — Zero Tolerance

После правки любого Python-файла — прогнать и исправить всё:

```bash
cd server && uv run ruff check . && uv run ruff format --check . && uv run mypy .
```

После правки любого файла в `frontend/`:

```bash
pnpm --dir frontend lint && pnpm --dir frontend typecheck
```

После изменения моделей — проверить миграции:

```bash
cd server && uv run alembic check
```

Тесты — `pytest` (+ `pytest-asyncio` для FastAPI), `Jest`/RTL для `frontend/`.
Пишем позитивные и негативные кейсы; идемпотентные операции (эскалация,
реиндексация) — вызываем дважды в тесте. Если нужного инструмента/скрипта нет
в проекте — сказать явно, не пропускать проверку молча.

## Git & Commits

- **Conventional Commits**: `feat:`, `fix:`, `docs:`, `refactor:`, со скоупом
  где уместно (`feat(rag): ...`, `feat(channels): ...`). Описание коммита —
  на русском (`feat(rag): добавить чанкинг документов`).
- Без force push без обсуждения. Коммитим/пушим только когда попросили.
- Перед крупным рефакторингом, который может требовать отдельную ветку —
  спросить.
